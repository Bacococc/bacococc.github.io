## Process / Port / Linux / 실행 구조

우리가 작성한 코드가 실제 서버 환경에서 어떻게 움직이는지 이해하기 위해, 다음과 같은 질문을 시작으로 전체 과정을 알아볼 것이다. 위의 4가지 개념을 이해하기 위해 다음과 같은 질문에 답을 하며 학습할 것이다.

> **핵심 질문: "브라우저에서 API를 요청하면 서버 내부에서는 정확히 무슨 일이 일어날까?"**

```text
Browser ──> [ ? ] ──> Server ──> [ ? ] ──> NestJS API
```

브라우저에서 API를 요청한 후 서버 내부에서 일어나는 일련의 과정을 통해 물음표(`?`)에 해당하는 과정을 구체적으로 파악하고자 한다. 

이번 파트의 목표는 **"우리 웹사이트의 서버가 Linux 환경에서 실행될 때, Process / Port / Socket이 어떤 관계로 연결되어 동작하고 실제 요청이 어떻게 들어오는가?"**를 이해하는 것이다.

최종적으로 머릿속에 그려야 할 서버 내부의 실행 구조는 다음과 같다.

## 왜 서버에서는 Linux를 사용할까?

Linux는 운영체제(OS)의 한 종류로, 특히 웹 서버나 데이터베이스 서버 등 대다수의 서버 인프라 환경에서 압도적으로 많이 사용된다. 서버 인프라에서 Linux를 사용하는 대표적인 이유는 다음과 같다.

1. **안정성 (Stability)**: 서버는 오랜 시간 동안 중단되지 않고 365일 안정적으로 동작해야 한다. Linux는 수십 년간 서버용 OS로 거듭나며 시스템 다운타임이 매우 적은 안정적인 구조를 갖추었다.
2. **성능과 자원 효율성 (Efficiency)**: Linux는 윈도우나 맥에 비해 GUI(그래픽 화면)가 기본적으로 구동되지 않고 비교적 가볍다. 덕분에 적은 시스템 자원(CPU, Memory)으로 구동이 가능하므로, 서버의 연산 능력을 우리가 실행할 Node.js/NestJS 애플리케이션에 최대한 집중시킬 수 있다.
3. **명령어 기반의 관리와 자동화 (Automation)**: 터미널 셸(Shell)과 SSH를 통해 마우스 없이 키보드 입력(명령어)만으로 프로그램을 실행, 정지, 모니터링할 수 있다. 이는 스크립트 작성을 통한 인프라 자동화에 매우 적합하다.
4. **오픈소스와 비용 절감 (Open Source)**: OS 라이선스 비용이 들지 않으며, 개발자 생태계가 매우 거대하여 다양한 서버용 오픈소스 소프트웨어를 쉽게 설치하고 커스터마이징할 수 있다.

## Program vs Process

```text
Program
  ↓ (실행)
Process (PID 발급)
  ↓
CPU / Memory 자원 사용
```

이 챕터에서 다룰 내용은 다음과 같다.

* Program과 Process의 개념 차이
* Process ID(PID)의 역할
* Process가 실행될 때 CPU와 Memory를 사용하는 방식
* Linux 운영체제가 Process를 관리한다는 의미

### Program (프로그램)
* **정의**: 디스크에 저장되어 있는 실행 파일이자, 컴퓨터가 수행할 명령어들의 집합
* **예시**: 작성된 NestJS 프로젝트 폴더 내부의 코드 파일들 (`main.ts`, `app.module.ts` 등)은 아직 작동하지 않는 Program 상태

```text
NestJS 프로젝트 (실행 파일 상태 = Program)
├── main.ts
├── app.module.ts
├── controller
└── service
```

위와 같은 프로젝트 폴더 구조를 갖추고 있는 상태이다. 이 코드 자체는 아직 실제로 가동되고 있지 않으므로 Program 상태이다. 요리에 비유하자면, 아직 요리를 시작하지 않은 상태의 '레시피'라고 할 수 있다.

### Process (프로세스)
* **정의**: Program이 실제로 메모리에 적재되어 실행 중인 상태를 말한다. 즉, **현재 실행 중인 프로그램의 인스턴스**
* **예시**: 프로젝트 폴더에서 `npm run start` 명령어를 입력해 가동하면, 운영체제(OS)에서 실행 중인 하나의 Node.js Process가 만들어짐

```text
레시피 (Program, 디스크의 파일)
  ↓ 요리 시작 (npm run start)
만들어지고 있는 요리 (Process, 메모리 실행 상태)
```

프로세스는 컴퓨터의 메모리 공간에서 실행된다고 하는데, 그렇다면 이 메모리란 무엇인가?

### 프로세스를 실행하기 위한 자원: CPU와 Memory
Process가 실제로 실행되어 제 역할을 하려면 시스템 자원이 필요하다.

```text
                 Process
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
        CPU                Memory (RAM)
    (명령어 처리)          (임시 작업 공간)
```

* **CPU (중앙처리장치)**: 프로그램의 명령어를 읽고, 해석하여, 실제로 계산을 수행하는 핵심 장치. 프로세스가 작업을 수행하기 위해서는 반드시 CPU의 연산 능력을 빌려 써야 함.(비유: **주방에서 일하는 요리사**)
* **Memory (RAM, 주기억장치)**: 프로세스가 실행되는 동안 필요한 변수, 객체, 실행 코드 등을 돌리는 임시 작업 공간.(비유: **요리 재료들을 펼쳐두고 조리하는 조리대**)

여기서 말하는 Memory란 컴퓨터의 RAM(주기억장치)을 의미한다.

예를 들어 Node.js 프로그램이 실행을 시작하면 다음과 같은 자원들이 메모리(RAM) 공간을 차지하게 된다.

```text
Node Process
 ├── 실행할 코드
 ├── 변수
 ├── 객체
 ├── 요청 처리에 필요한 데이터
 └── 기타 Runtime 정보
          ↓
       Memory(RAM)
```

```text
CPU = 일하는 사람
Memory = 작업 공간
```

```text
HTTP 요청
   ↓
Node Process
   ↓
CPU가 코드 실행
   ↓
결과 생성
   ↓
Response
```

## Linux에서 Process는 어떻게 관리되는가?

학습할 내용은 다음과 같다.

* Linux Process의 기본 개념
* Process ID (PID)
* CPU 및 Memory 사용량 확인
* Process 상태 변화
* `ps` 명령어
* `top` 명령어

리눅스 터미널에서 다음 명령어를 입력하여 Node.js가 실제로 하나의 Process로 실행되고 있는지 확인한다.

* `ps aux | grep node`  
* `top`

이 명령어들을 통해 Node.js 서버 프로세스가 실행 중인 것을 직접 확인해 볼 수 있다.

여기서 중요한 개념은, 하나의 Program 파일을 가지고 여러 개의 Process를 동시에 실행시킬 수 있다는 점이다.

만약 한 프로그램을 여러 번 실행하게 된다면 다음과 같은 구조로 실행된다.

```text
Program
   │
   ├── Process A (PID 1001)
   ├── Process B (PID 1002)
   └── Process C (PID 1003)
```

위의 그림처럼 개별 프로세스로 실행되는 구조이다.

운영체제는 시스템 안에 수많은 Process가 동시에 존재하므로, 이들을 서로 혼동하지 않기 위해 고유한 번호인 Process ID(PID)를 발급하여 구분한다.

PID는 단순히 프로세스들을 구분하는 용도로만 쓰는 것이 아니다. `kill 1234`와 같이 특정 PID를 지정하여 해당 프로세스를 종료하는 등, 특정 프로세스를 직접 제어하는 명령을 내릴 때 사용된다.

## Process만 있으면 요청을 받을 수 있을까?

Node Process가 실행 중이라고 해서 `localhost:8080`으로 요청을 보낼 수 있는 것은 아니다.

```text
Process
   ↓
??? 
   ↓
Port
```

학습할 내용은 다음과 같다.

* IP와 Port의 역할
* 왜 Port가 필요한가
* Process와 Port의 관계
* Well-known Port의 종류

### IP (Internet Protocol)
* **IP** 란 네트워크에서 어떤 장치/인터페이스를 찾아가기 위한 주소

하지만 IP 만으로는 정확한 목적지를 찾아가기에는 부족하다. 서버 한대에서 여러 네트워크 서비스가 실행되고 있을 수 있기 때문이다. 
알기 쉽게 예를 들자면, 우리가 로컬로 개발중일 때 조차 `localhost:3000` `localhost:8080` 등 여러 **port**를 열어놓고 개발한다. 여기서 포트 번호가 없다면 한대의 컴퓨터 안에서 조차 어떤 프로그램에게 요청을 전달해야 하는지 알 수 없다. 마치 아파트 이름 만으로는 몇 호에 사는 사람인지 알 수 없는 것과 같다.

### Port (포트)
* **Port**: 네트워크 통신에서 특정 서비스/프로세스와 연결하기 위한 논리적인 번호
`192.168.0.10:8080` 과 같은 IP와 port 번호가 있다면, IP는 어느 호스트로 갈 것인지, Port는 그 호스트에서 어느 네트워크 서비스로 갈 것인지 식별하는 데 사용된다.

#### Port ≠ Process
포트 번호 자체는 프로세스가 아니다. 포트는 OS 레벨에서 개방해 주는 네트워크 종단점 번호이고, 프로세스가 이 포트를 선점하고 있어야 실제 네트워크 패킷을 받아 통신할 수 있다.

#### Well-known Port (웰노운 포트)
전 세계적으로 대표적인 네트워크 서비스들에 대해 미리 약속하여 할당해 둔 포트 번호를 말한다. 일반적으로 `0`번부터 `1023`번 포트까지가 이에 해당하며, 관리자 권한(root)이 있어야만 열 수 있다.
* `22` : SSH (원격 접속 프로토콜)
* `53` : DNS (도메인 네임 시스템)
* `80` : HTTP (기본 웹 통신 프로토콜)
* `443` : HTTPS (보안 적용 웹 통신 프로토콜)

## Socket / Bind / Listen

```text
Node.js Process
      │
      │ ① Socket()
      ↓
   Socket
      │
      │ ② Bind()
      ↓
 0.0.0.0:8080
      │
      │ ③ Listen()
      ↓
  연결을 기다림
```

“그럼 Process가 어떻게 Port를 사용하는가?”

* Socket
* Bind
* Listen

### Socket (소켓)
* **정의**: Process가 네트워크 통신을 하기 위해 사용하는 소프트웨어적 창구(인터페이스)
* **설명**: 프로세스가 네트워크로 데이터를 보내거나 받으려면 OS에게 "네트워크 창구를 개설해 줘"라고 요청해 소켓을 만들어야 한다.

### Bind (바인드)
* **정의**: 생성된 Socket에 특정 IP 주소와 Port 번호를 연결하는 과정
* **설명**: 소켓 창구만 개설한다고 해서 끝나는 것이 아니다. "이 소켓 창구는 `0.0.0.0` 주소의 `8080`번 포트로 드나드는 연결에 사용하겠다"라고 확실하게 지정하는 과정

### Listen (리슨)
* **정의**: Socket에 IP와 Port가 바인딩된 후, 들어오는 연결 요청을 기다리는 상태로 만드는 과정
* **설명**: 바인드까지 마친 소켓을 `Listen` 상태로 활성화해야 비로소 외부 클라이언트가 해당 포트로 보낸 TCP 연결을 수락하고 대기시킬 수 있는 준비가 완료됨

#### 셋을 한 번에 이해하기 (NestJS 예시)
예를 들어 NestJS(또는 Node.js 백엔드)가 `8080` 포트에서 가동될 때 내부 동작은 다음과 같다.

1. **① Socket 생성**: Node Process가 통신 창구(Socket)를 만든다. ("네트워크 통신용 소켓을 생성.")
2. **② Bind**: 소켓에 IP와 Port를 바인딩한다. ("이 소켓을 `0.0.0.0:8080` 바인딩.")
3. **③ Listen**: 연결 수신 대기 상태로 만든다. ("이제 `8080` 포트로 들어오는 요청을 받을 준비를 마침")

```text
                    Server
                      │
Node Process          │
     │                │
     ▼                │
  Socket              │
     │                │
     ▼                │
    Bind              │
     │                │
     ▼                │
0.0.0.0:8080          │
     │                │
     ▼                │
   Listen ◀──────── HTTP Request
     │
     ▼
연결 처리
     │
     ▼
   NestJS
```

*node의 `server.listen()`은 포트번호를 점유하여 대기하는 '서버 소켓'을 열어두는 것이며, 실제 클라이언트가 해당 주소에 접속할 때마다 실시간으로 일대일 통신을 위한 '클라이언트 소켓'이 내부적으로 재생성되어 연결을 처리한다.*

## localhost / 127.0.0.1 / 0.0.0.0

```text
localhost
   ↓ (매핑)
127.0.0.1 (Loopback)
   vs
0.0.0.0 (Wildcard)
```

서버 개발 과정에서 흔히 마주치는 네트워크 주소 표현의 차이점을 구별해야 한다.

### 127.0.0.1 (Loopback 주소)
* **의미**: 자기 자신(로컬 호스트)을 가리키는 특수한 IP 주소이다.
* **특징**: 네트워크 카드를 거치지 않고 운영체제 내부에서 즉시 되돌아오는 루프백 인터페이스이다. **외부 장치에서는 절대로 이 주소를 통해 접속할 수 없으며**, 서버가 구동 중인 본인 컴퓨터 내부에서만 접속이 허용된다. 즉, 나 자신만 통신 가능하다는 의미이다.

### 0.0.0.0 (Wildcard 주소)
* **의미**: 시스템에 부여된 모든 네트워크 인터페이스(IP) 주소들을 전부 의미한다.
* **특징**: 서버가 `0.0.0.0:8080`으로 바인드하여 Listen하게 되면, 서버에 장착된 무선 LAN(Wifi) IP로 들어오는 요청이든, 유선 LAN IP로 들어오는 요청이든, Loopback(`127.0.0.1`)으로 들어오는 요청이든 **8080번 포트로 오기만 하면 전부 허용하고 처리하겠다**는 의미이다.
* *주의*: 클라이언트가 서버로 실제 접속할 때는 주소창에 `0.0.0.0:8080`으로 타이핑해서는 안 된다. `0.0.0.0`은 서버 리슨 설정의 주소 표현일 뿐이며, 클라이언트는 실제 서버 장비의 IP 주소(예: `192.168.0.10:8080` 또는 AWS EC2의 공인 IP)를 치고 들어와야 한다.

## 실제 서버에서 동작 확인하기

이론적으로 공부한 Process, Port, Socket, Listen의 유기적인 결합 상태는 Linux 터미널 명령어를 통해 직접 추적하고 검증할 수 있다.

```text
Node.js Process (ps aux)
       ↓
8080 Port LISTEN (ss -lntp)
       ↓
HTTP Request (curl /health)
       ↓
API Response
```

### 1. 프로세스 작동 상태 조회
현재 시스템에 Node.js Process가 구동 중인지, 그리고 OS가 부여한 고유 PID는 몇 번인지 확인한다.
```bash
$ ps aux | grep node
```
* **출력 예시**:
  ```text
  USER       PID  %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
  hyojin   77149   0.5  0.8 123456 45678 pts/1    Sl   12:00   0:05 node server.js
  ```
  현재 실행 중인 프로세스의 PID가 **`77149`**인 것을 확인할 수 있다.

### 2. 포트 및 소켓 연결 대기 상태 조회
네트워크 포트가 실제로 프로세스 소켓에 정상 바인드되어 Listen 상태로 응답을 기다리고 있는지 점검한다.
```bash
$ ss -lntp
# (macOS 등 BSD 계열은 lsof -iTCP -sTCP:LISTEN 실행)
```
* **출력 예시**:
  ```text
  State      Recv-Q Send-Q   Local Address:Port   Peer Address:Port   Process
  LISTEN     0      128            0.0.0.0:8080        0.0.0.0:*      users:(("node",pid=77149,fd=12))
  ```
  PID `77149`를 가진 `node` 프로세스가 모든 인터페이스(`0.0.0.0`)의 `8080`번 포트에서 **`LISTEN`** 상태로 소켓을 개방하여 대기하고 있는 것을 확인할 수 있다.

### 3. API 통신 정상 동작 확인
가상 클라이언트 도구인 `curl` 명령어로 실제 HTTP Request를 발송해 정상 응답을 돌려받는지 확인한다.
```bash
$ curl localhost:8080/health
```
* **출력 예시**:
  ```json
  {"status":"ok","message":"Healthy","pid":77149}
  ```
  이를 통해 `Node Process ──> 8080 Port ──> LISTEN ──> HTTP Request ──> API Response`로 이어지는 서버 인프라 정상 흐름이 완전히 동작하고 있음을 입증할 수 있다.

## 장애 실험을 통해 알아보는 서버의 상태

실무 환경에서는 인프라 장애나 서버 먹통 원인을 정확하게 짚어내는 역량이 필수적이다. 프로세스 중단 및 로직 실패 상황을 각각 시뮬레이션함으로써, 서버의 세부 계층별 장애 차이를 공부한다.

### 장애 A: 프로세스 다운 (Process Down)
프로세스 자체가 아예 강제로 종료되어 기동되지 않는 인프라 중단 현상이다.

1. **상황 발생**: 확인해 둔 Node.js 프로세스의 PID(`77149`)를 강제 종료한다.
   ```bash
   $ kill 77149
   ```
2. **상태 조회**:
   * `ps aux | grep node` 실행 시 검색되는 프로세스가 사라진다.
   * `ss -lntp` 실행 시 `8080` 포트의 LISTEN 라인이 목록에서 깔끔하게 증발한다.
3. **요청 결과**:
   ```bash
   $ curl localhost:8080/health
   curl: (7) Failed to connect to localhost port 8080: Connection refused
   ```
   소켓 창구 자체가 사라졌으므로 운영체제가 즉각 **Connection Refused (연결 거부)** 에러를 발생시킨다.
4. **교훈**: 호스트 머신(EC2나 PC)의 전원이 켜져 있고 서버 장비가 정상 생존해 있다고 해서, 내부의 백엔드 프로세스(Node.js)도 당연히 정상 가동 중일 것이라고 예단해서는 안 된다.

### 장애 B: 애플리케이션 및 내부 로직 장애 (Application Error)
프로세스 소켓도 열려 있고 포트도 LISTEN 상태이지만, 데이터베이스 오작동 등 백엔드 로직에 내부 장애가 발생한 상태이다.

1. **상황 발생**: 테스트 서버에 설정된 장애 유도 API를 임의로 트리거하여 헬스 상태를 강제 변경한다.
   ```bash
   $ curl localhost:8080/make-unhealthy
   {"message":"서버 상태를 강제로 [장애(Unhealthy)] 상태로 변경했습니다."}
   ```
2. **상태 조회**:
   * `ps aux | grep node` 실행 시 프로세스는 버젓이 가동되고 있다.
   * `ss -lntp` 실행 시 `8080` 포트 또한 정상적인 `LISTEN` 상태를 고스란히 유지한다.
3. **요청 결과**:
   ```bash
   $ curl localhost:8080/health
   {"status":"error","message":"Internal Server Error (Database Connection Failed)","pid":77149}
   ```
   서버와의 네트워크 포트 소켓 연결은 정상적으로 이루어져 패킷이 프로세스까지 전달되지만, 프로세스가 500 에러와 함께 DB 통신 에러 메시지를 반환한다.
4. **교훈**: 포트가 개방(LISTEN)되어 접속이 된다고 해서 해당 API 서비스가 정상 기능을 제공한다는 뜻은 아니다. 내부 데이터베이스나 서드파티 연결부에서 로직 장애가 발생해 동작이 마비되었을 수 있다.

### 핵심 요약: 3단계 헬스체크
서버 운영 및 트러블슈팅을 진행할 때는 다음 **3단계 헬스체크**가 모두 통과되어야만 진정으로 서비스가 완전 정상이라고 진단할 수 있다.

```text
  1단계: Process 상태 (ps)  ──>  프로세스가 살아 숨 쉬고 있는가? (프로세스 다운 장애 감지)
            ↓
  2단계: Port LISTEN 상태 (ss) ──> 포트가 열려 소켓이 연결을 수락하는가? (포트/인프라 장애 감지)
            ↓
  3단계: Application 상태 (curl) ──> 내부 로직(DB 등)이 에러 없이 응답을 돌려주는가? (애플리케이션 장애 감지)
```

## 우리 웹사이트에서 어디에 사용되는가?

```text
                  Internet
                     │
                     ↓
                  EC2
                     │
                  Linux
                     │
             ┌───────┴───────┐
             ↓               ↓
          Nginx          Node Process
          :443                │
                              ↓
                           NestJS
                              │
                           :8080 (or :4000)
                              │
                              ↓
                           MySQL
```

우리가 공부한 이 개념들은 실제 프로젝트 인프라 아키텍처에 고스란히 투영된다.
* **EC2 & Linux**: 우리 서버가 돌아갈 하드웨어 및 OS 물리/가상 인프라이다.
* **Nginx (:443)**: 외부 사용자가 인터넷망을 통해 HTTPS 보안 연결을 타고 들어오면 가장 먼저 수신을 담당하는 웹 서버 프로세스이다.
* **Node.js & NestJS (:8080)**: Nginx가 요청을 가공해 로컬 소켓에 바인딩된 Node 프로세스로 패킷을 토스(Proxy)해 주면, 백엔드 애플리케이션 코드가 처리한다.
* **MySQL**: 최종 데이터를 연산하기 위해 Node 프로세스 소켓을 거쳐 영속성 데이터를 조작하는 관계형 데이터베이스 프로세스이다.

## 정리

```text
Program
  ↓
실행
  ↓
Process
  ↓
PID
  ↓
CPU / Memory 사용
  ↓
Socket
  ↓
Bind
  ↓
IP + Port
  ↓
Listen
  ↓
HTTP Request
  ↓
Application
  ↓
Response
```

가장 명심해야 할 최종 핵심 교훈은 다음과 같다.

> **"서버가 살아있다"는 단 하나의 통합된 상태를 뜻하는 것이 결코 아니다.**

```text
AWS EC2 인스턴스가 가동 중이다 (서버 장비)
       ≠
Node.js 프로세스가 가동 중이다 (프로세스)
       ≠
네트워크 포트가 LISTEN 상태이다 (포트/소켓)
       ≠
API 로직이 에러 없이 정상 결과물을 응답한다 (애플리케이션)
```

이 4가지 계층 상태는 엄연히 별개이다. 이를 구분해 낼 줄 알아야 장애가 났을 때 우왕좌왕하지 않고 어느 레이어가 깨졌는지 단계적으로 원인을 추적할 수 있다.
